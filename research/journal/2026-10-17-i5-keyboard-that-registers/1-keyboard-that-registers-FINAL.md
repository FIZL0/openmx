# 1 — keyboard that registers (FINAL)

Task I5. 2026-10-17.

## What I did

Two bugs, one in each file the task names, both of them the shell taking a host input source literally
when it should have been interpreting it.

**`window.rs`: a held key flickered.** The key table was written straight off the X11 wire — `KeyPress`
sets a bit, `KeyRelease` clears it — and X's core auto-repeat does not leave a held key down. About
thirty times a second it delivers a `KeyRelease` immediately followed by a `KeyPress` of the same
keycode, both stamped with the same server time. Read literally that is a key going up and down thirty
times a second: `Window::held` dropped false for whichever frame landed between the two halves, and
`game_sim::input`'s press and release edges (I1's timers and its event queue) saw dozens of taps where
a person held one button.

The key state is now a small `Keyboard` struct in the same module, and a release is no longer applied
when it arrives. It waits for the event after it; if that event is a press of the same keycode within
`REPEAT_MS` (2 ms of slack on what is normally an identical timestamp), the pair was a repeat and the
key never came up. Anything else behind the release — another key, a later press of the same key, or
nothing at all, which is what `Keyboard::settle` says when the socket runs dry at the end of a `poll`
— is a person letting go, and the release applies then. The two halves of a repeat are generated by
one server operation and written to the socket together, so settling at the end of a poll does not
split a pair, and a real release still lands on the frame it arrived in: no latency was added.

I did **not** take the task's other option, `ChangeKeyboardControl` (opcode 102). It would have suited
the module — no reply, one request at startup — but `auto-repeat-mode` is a property of the server's
keyboard and not of one window: turning it off stops the user's whole session repeating, including in
the terminal the shell was started from, and leaves it off if the shell dies before putting it back
(this shell exits on a window-manager close and on an error from `present`, so "putting it back" is not
a single code path). Reading the stream correctly costs one `Option` and changes nothing outside the
struct. The XKB way to ask for exactly this per client, `XkbSetDetectableAutorepeat`, needs the XKB
extension, which needs a reply-bearing `QueryExtension`, which is the one thing this module is built
not to do.

**`pad.rs`: the keyboard sticks slammed.** `key_axis` answered 0, 255 or centre, so a direction key was
full deflection on the frame it went down. Through I2's measured stick curve — a dead zone of a fifth
of the travel either side of centre, then a 1.25× segment — that makes lean, steer and preload
all-or-nothing: there is no small input a keyboard can express, and a tap is full lock.

`KeyAxis` replaces it: one per stick axis, four of them in `Pads`, each holding where its stick has
got to as a fraction of full deflection. A held key ramps it toward the edge over `KEY_TO_EDGE`
(0.18 s, ~11 frames at 60 Hz), letting go brings it home over the quicker `KEY_TO_CENTRE` (0.10 s), and
both keys at once is treated as letting go rather than as a stop. The axis answers `None` only once it
has settled at centre with neither key down, which keeps the old property that a pad's own stick owns
an axis the keyboard is not touching. The step is in seconds, not frames — `Pads` times its own
reports, because the loop paces to 60 Hz but a heavy frame overruns, and a keyboard that leaned
further when the picture was cheap would be its own bug — and one step is capped at `KEY_STEP_MAX`
(1/15 s) so a stalled frame cannot hand the ramp a tenth of a second of travel at once. The byte comes
out of the same `stick_byte` the pad's own axes use, so a key and a stick at equal deflection report
equal bytes.

Side effects of the ramp, on purpose: the first ~36 ms of a held key is the stick crossing I2's dead
zone, so a one-frame tap is now *no* steering input at all rather than full lock, and a change of
direction passes through centre at the return rate instead of jumping across.

## What the original does

Nothing: there is no original to match here. The disc's input is a DualShock 2 and the port reads its
32-byte report unchanged (`game_sim::input`, I1/I2) — both files in this task are the host shell that
manufactures those bytes, and neither touches the simulation's own arithmetic. The two durations are a
design decision, chosen against the one measured number in the area: I2's dead zone is a fifth of the
travel, so `KEY_TO_EDGE` is set long enough that crossing it takes two or three frames and the ride
grows out of nothing, rather than short enough to be indistinguishable from the slam it replaces.

## How it was proved

Unit tests in both modules, through `./kit check` (471 tests pass, 6 of them new):

- `window::tests::an_auto_repeat_pair_leaves_the_key_held` — an event stream built as the server writes
  it (32-byte events, keycode in `detail`, timestamp in the first four-byte field): a press, then five
  frames' worth of release/press pairs at thirty a second, then a real release. The key is held
  throughout and comes up at the end. A pair stamped a millisecond apart is in there too, for the slack.
- `window::tests::a_repeat_does_not_blink_even_part_way_through_the_stream` — the release half on its
  own, with the press half still in the socket and nothing settled: `held` must not have moved. This is
  the exact frame the old reader lost.
- `window::tests::a_release_is_believed_whatever_follows_it` — a release with another key's press
  behind it, and a real tap of the same key 80 ms later: both clear the key.
- `pad::tests::a_held_direction_reaches_the_edge_over_several_frames` — one 60 Hz frame of a held key
  is off centre and nowhere near the stop; the edge arrives after 8–15 frames, climbing every frame;
  letting go comes home quicker and then answers `None` so the pad gets its axis back.
- `pad::tests::the_low_key_goes_the_other_way_and_the_two_together_come_home` — the low key reaches 0,
  both keys together head home, and a reversal from the far stop takes at least five frames to cross
  centre.
- `pad::tests::a_tap_no_longer_slams_the_game_s_own_axis` — the frame-one byte put through the port's
  own `Manager` reads exactly `F(0.0)`: still inside I2's dead zone. The same test asserts that the
  byte the module used to answer on that frame, 255, reads `AxisRange::STICK.hi` — the before and the
  after of the bug, in one place.

Live: `cargo run -p openmx -- --seconds 6` opens the window, rides and quits at 59.8 fps with the new
poll and the four ramped axes being stepped every frame — the same numbers as before the change.

## Not verified / not 1:1

- **The timestamp equality of a repeat pair is not observed on this display.** The filter rests on the
  X server generating a repeat's `KeyRelease` and `KeyPress` with the same timestamp (the behaviour XKB
  added detectable auto-repeat to avoid, and what GLFW and SDL both match on). I could not watch it
  happen here: this desktop delivers no keystrokes to a window an agent opens, and the one way to
  generate a repeat without a human — XTEST fake input — would have landed a real keypress in whatever
  window the compositor actually has focused, which is the user's. It fails safe: if some server
  stamped the two halves more than `REPEAT_MS` apart, the pair reads as a genuine release and press,
  which is exactly today's behaviour and no worse.
- **No human has held a key down and said whether it registers.** The bug this task is named for
  ("i cant tell my keys are doing anything") is a feel report, and the fix is only proved against the
  numbers: the dead zone it now crosses, and the frames it takes. The two durations are open to being
  re-tuned by whoever rides it first.
- **`Pads::report`'s own wiring is not unit-tested** — only `KeyAxis` is. Building a report needs a
  live `Window`, so a test of it would need an X display, which a unit test must not. What the 6 s ride
  proves is that the path runs every frame; which key moves which axis (`KEY_STICKS`) is only read, not
  asserted.
- **Nothing here is 1:1 with the original by nature.** Auto-repeat filtering and keyboard stick ramps
  have no counterpart on a PS2: the simulation sees report bytes either way, and this task changed only
  which bytes a keyboard produces. No simulation arithmetic, RNG or timing was touched, and the replay
  fixtures (which feed reports, not keys) are unaffected — 471 tests pass unchanged.
