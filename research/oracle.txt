# O1 — the functions the oracle was proved on. Chosen for being too small to be wrong about: a handful
# of instructions each, no globals, no calls, no allocation, so a disagreement can only be the
# interpreter. Together they still cover the FPU accumulator chain, sqrt, max/min, VU0 macro mode,
# quadword loads and stores, out-parameters and one data-dependent loop. All of them are the game's own
# inlined maths helpers, emitted once per header and called from everywhere.
# crates/ps2-oracle/tests/basics.rs calls every one of these; how it was done is in
# research/journal/2026-10-15-o1-oracle.
#
# Scalars, in f12/f13, result in f0. One instruction each.
float_max                   boot 0x00107f80 max.s: (a, b) -> the larger. The game has no clamp of its
#                                           own — call sites compose this with float_min
float_min                   boot 0x00107f90 min.s: (a, b) -> the smaller
float_abs                   boot 0x00107fe0 abs.s: (x) -> |x|
#
# Vec3, by pointer. The quadword forms read and write all four lanes, so the w lane must hold something
# defined even when only xyz are wanted.
vec3_dot                    boot 0x00107ff0 (a, b) -> dot, as mula.s/madda.s/madd.s in index order
vec3_length                 boot 0x00108920 (v) -> sqrt of that same chain over (v, v)
vec3_length_sq              boot 0x0010b270 (v) -> the chain without the sqrt. Identical code also at
#                                           0x0010b260 (a thunk) and 0x0010b250 thunks vec3_length
vec3_add                    boot 0x00111e60 (out, a, b): three add.s, three swc1 — out may alias
vec3_sub                    boot 0x00111ea0 (out, a, b): the same with sub.s
vec3_scale                  boot 0x00108890 (out, v, s in f12): VU0 macro, vmulx.xyz off a broadcast of
#                                           s; w comes back from v untouched. 0x001088c0 is identical
vec3_normalize              boot 0x00108070 (out, v): vmul/vadda/vmadd for the square, then vrsqrt —
#                                           the VU approximation, not a correctly rounded one
vec4_abs                    boot 0x00108020 (out, v): builds 0x7fffffff in four lanes with lui/ori,

keyframe_index_stride2      boot 0x001361e0 (t in f12, table, n) -> how many keys are at or before t:

# I1 — the input layer. The pad poll's timer update is not a function: it is a span inside the poll,
# so the test loads these instructions into a bare interpreter and appends its own `jr $ra`. The name
# is the span's first instruction; the length is in the test.
pad_timer_add_ms            boot 0x0016aef0 30 instructions, not a function: ($s2+0x330) += $f20 ms,
#                                           where the stored value is read back as *unsigned* (bltz,
#                                           then halve-convert-double) and the sum converted back as
#                                           unsigned (c.ole.s against 2^31, then subtract the bias and
#                                           set the sign bit by hand). Falls through to the span's end,
#                                           so the test's `jr $ra` sits where the poll's `b` went.
#                                           The identical sequence at 0x0016ae68 does +0x334 (held ms)

# ---------------------------------------------------------------------------------------------------
# O2 — the arithmetic carriers. No shipped game has a function that is one `div.s` and a `jr`, so the
# oracle coverage of F1-F3 runs each op through the smallest *call-free* function in the image that
# contains it: one or two operations wide, every input an argument or a field the test writes, every
# result still readable when the function returns. They were found by disassembling every call-free
# function and looking for the ops the O1 set never reaches. crates/ps2-float/tests/oracle.rs calls
# each one over 10k generated inputs from the awkward classes — zero and minus zero, both ends of the
# denormal range, the smallest normal, the largest magnitudes, the Inf and NaN patterns the EE has not
# got, powers of two, and *pairs* with a chosen exponent difference (0, 24, 25, 26 and more). How it
# was done, and what it cannot prove, is in research/journal/2026-10-15-o2-float-oracle.
#
# The scalar FPU. Offsets are into the object the carrier is a method of; the test writes the fields it
# reads, so no RAM image is needed.
float_mul_add_into          boot 0x0025d180 (obj, a in f12, b in f13): *(obj+0x6c) += b*a as a mul.s and
#                                           then a separate add.s, with the sum also left in f0. Both
#                                           factors are arguments, so this is the full-domain mul.s
float_recip_32767           boot 0x00388a50 (obj, x): obj+0x94 = x, obj+0x90 = 32767.0 / x. div.s with
#                                           a free divisor, zero and the denormals included
float_span_rate             boot 0x002f9ab0 (obj, a, b): obj+0x64 = max(a, obj+0x64); obj+0x6c = 0.5 *
#                                           that; obj+0x68 = (b - obj+0x5c) / obj+0x6c. div.s with a
#                                           free numerator, plus max.s, mul.s and sub.s in that order
float_inv_sqrt              boot 0x00284b80 (x) -> 1.0 / sqrt(x): one rsqrt.s against a lui-built one.
#                                           The only root carrier that takes its argument whole, so the
#                                           only one that can be given a negative or a denormal
quat_two_matrix_rows        boot 0x0013f380 (q, row_a, row_b): two rows of the rotation matrix of the
#                                           quaternion at q, as eleven mul.s, two add.s, three sub.s and
#                                           the accumulator pairs mula.s/msub.s (-> row_b+0) and
#                                           mula.s/madd.s (-> row_a+0). The only call-free msub.s in the
#                                           image whose result is not overwritten before the return
float_to_i16_pair           boot 0x00302ce0 (out, &a, &b): out[0] = (short)(int)a, out[1] the same for
#                                           b, as cvt.w.s + mfc1 + sh. Either half is skipped on a null
i16_pair_to_float           boot 0x00302d70 (src, &a, &b): a = (float)src[0], b = (float)src[1] from the

vec3_div_scalar             boot 0x001088f0 (v, s in f12) -> v: v.xyz *= 1/s in place, as a vdiv of

# --- F3: VU0 macro mode ------------------------------------------------------
# Call sites that exercise the vu.rs model. The first two are small and pure and are the cheapest way
# to prove VU0's divider and its chop against the real code; the last two need the MAC flag, which
# ps2-oracle's interpreter does not keep yet (it has no cfc2/$vi17).
vu_scale3_recip        boot  0x001088f0 9 insns: Q = 1.0/f12 (vdiv), then the xyz of the vec4 at a0 *= Q (vmulq.xyz), stored back; returns a0. Proves vdiv + vmulq.
vu_unpack_s8_to_vec3   boot  0x001008e0 4 signed bytes at a0 -> vitof0.xyz -> vmulx.xyz by a scale looked up at (byte0 * 8) in a table; result stored at a1.
vu_quat_to_mat3        boot  0x0013ebd0 quaternion at a1 -> three matrix rows; vadd/vmul broadcasts and vmr32.w row, vf0 to put 0 in each row's w.
vu_plane_side_w        boot  0x003dc320 a dot product accumulated into .w, then cfc2 $vi17 and andi 0x10 (the MAC Sw bit) to branch on "behind the plane".
# F4 — the transcendentals the disc actually links. The float set is fdlibm's `float` flavour (Sun's
# freely-distributable libm, as shipped in the SDK's libm.a), compiled with every decimal constant
# rounded *toward zero*: S1 is 0xbe2aaaaa, one ulp below fdlibm's own 0xbe2aaaab, and so on through
# every polynomial. There is **no atan2f and no expf/logf in the image at all** — see the journal entry
# research/journal/2026-10-15-f4-libm for the full inventory and for what the game uses instead.
# `sqrtf` is not a function: all 305 square roots are an inlined `sqrt.s`.
# sinf, cosf, atanf, powf, fmodf and sqrtf are proved bit-exact against crates/ps2-float/src/libm.rs
# over every exponent an f32 has: cargo test -p ps2-oracle --test libm (52k inputs).
#
# The float set. One argument in f12 (two for powf/fmodf: f12, f13), result in f0.
sinf                        boot 0x0040aac0 fdlibm sinf: |x|<pi/4 -> kernel_sinf, else rem_pio2f + the
#                                           kernel the quadrant picks. Only 3 call sites — the game does
#                                           its angles with its own helpers, not with libm
cosf                        boot 0x0040a820 fdlibm cosf, the same shape
powf                        boot 0x00406d20 fdlibm __ieee754_powf. 0x0040abf0 is the thunk the game calls
fmodf                       boot 0x00406b50 fdlibm __ieee754_fmodf: exact, integer shift-and-subtract,
#                                           no rounding anywhere. Thunk at 0x0040abd8, 15 call sites
sqrtf                       boot 0x0011b880 the game's own one-instruction sqrtf: `sqrt.s $f0,$f12` and
#                                           nothing else. Every other square root in the image (305 of
#                                           them) is the same instruction inlined, so this *is* the
#                                           game's sqrtf, and it rounds to nearest like all EE divides
atanf                       boot 0x0040a478 fdlibm atanf, aT[0..10] from the table at 0x0044aa5c. One
#                                           call site. No atan2f to pair it with
#
# The float internals, exposed because a disagreement in sinf is always in one of these.
kernel_sinf                 boot 0x00409900 (x, y, iy) -> sin(x+y) for |x| <= pi/4; iy!=0 means y matters
kernel_cosf                 boot 0x00408f48 (x, y) -> cos(x+y), with the 1-z/2 split above |x|>0.3
rem_pio2f                   boot 0x00407500 (x, &y[2]) -> n, y0+y1 = x - n*pi/2. Exact to |x| <= 2^7*pi/2
kernel_rem_pio2f            boot 0x00409098 the big fixed-point reduction rem_pio2f falls back to:
#                                           (x[], &y[2], e0, nx, prec, two_over_pi). rem_pio2f passes
#                                           prec=2 and the table at 0x0044a420 (198 ints, the 8-bit
#                                           digits of 2/pi). init_jk = {4,7,9} at 0x0044a9b8, and the
#                                           eleven pieces of pi/2 at 0x0044a9c8 (six of them one ulp
#                                           below fdlibm's source, the toward-zero rounding again)
floorf                      boot 0x0040a920 fdlibm s_floorf, called by kernel_rem_pio2f
scalbnf                     boot 0x0040a9f8 fdlibm s_scalbnf, but with no gradual-underflow path: below
#                                           the smallest normal it saturates to +-0 through tiny*tiny,
#                                           because this FPU has no denormals to return
copysignf                   boot 0x0040a7e0 sign bit of y onto x
fabsf                       boot 0x0040a8f8 and.s with 0x7fffffff, out of line

# F5 — the matrix and quaternion helpers for bones and cameras. The port is
# crates/game-sim/src/math.rs and the proofs are crates/game-sim/tests/math.rs; how each one was read
# is in research/journal/2026-10-15-f5-f5-matrix. Two of them are already listed above under their
# F1-F3 names and are not repeated here: `vu_quat_to_mat3` (0x0013ebd0) is the quaternion-and-position
# to 4x4 builder — it writes *four* rows, the position with w = 1 into row 3 — and
# `quat_two_matrix_rows` (0x0013f380) is the scalar pair of rows, a1 the forward axis (matrix row 2)
# and a2 the up axis (row 1).
#
# The 4x4 product is inlined everywhere and has no function of its own, so the carrier is the smallest
# call-free function that contains one. Note it overwrites two lanes of its right-hand matrix before
# loading it -- obj+0x68 and obj+0x78 are obj+0x40's lanes [2][2] and [3][2], and they get
# 1/(1 - f12/f13) and its negative times f12 -- so a test must read the matrix back out of RAM after
# the call and give *that* to the port. Generating f12 and f13 keeps those two lanes varying.
mat4_mul_carrier       boot 0x001131d0 (obj, f12, f13): obj+0xc0 = obj+0x80 * obj+0x40, four
#                                      vmulax/vmadday/vmaddaz/vmaddw chains, one per row of the left
#                                      matrix. Also writes obj+0x68, +0x78, +0x19c and +0x1a0
mat4_transform_points  boot 0x0013e3f0 (out, src, mat, n, out_stride, in_stride): n points through
#                                      mat, all four lanes out, the input's w lane replaced by 1.0
#                                      first (vaddx.w off vf0). in_stride 0 means "same as out_stride";
#                                      n <= 0 does nothing
mat4_basis             boot 0x0013e330 (out, pos, forward, up, orthogonalise, keep_forward): the
#                                      look-at. row1 = normalised up, row2 = normalised forward, row0
#                                      their cross, row3 = pos with w = 1, the other three w = 0. With
#                                      orthogonalise set, right = up x forward first and then either
#                                      up = forward x right (keep_forward) or forward = right x up.
#                                      Both normalisations are vrsqrt, the approximate one
quat_deriv             boot 0x0013ec40 (out, q, omega): 0.5*(q (x) omega) for a pure omega, as
#                                      vopmula/vmaddaw/vopmsub for the vector part and three
#                                      separately-halved products for the scalar. The half comes from
#                                      a constant quadword (0.5, 0.5, 0.5, -0.5), so the w lane is not
#                                      a dot product halved
quat_slerp             boot 0x0013ee10 (out, a, b, t in f12, shortest): spherical interpolation.
#                                      Returns a unchanged when |dot4(a, b)| >= 1 — it branches over
#                                      its own store. The angle is the shared acos table
#                                      (acos_table_ptr/-_scale above) read as lo - w*lo + w*hi through
#                                      the FPU accumulator, which is a different order from the
#                                      crossup's lookup; the three sines are a 7th-order Taylor
#                                      polynomial on VU0, three lanes at once, constants at 0x00426e10
mat4_to_quat           boot 0x0013f7b0 (out, mat): the rotation back to a quaternion by largest of the
#                                      four 0.25*(1 +- m00 +- m11 +- m22) candidates, each compared
#                                      with <= so a tie loses. Scalar FPU: sqrt.s then 0.25/it

# S4 — collision against the world. The sweep and the shape test, as the sphere/probe-bundle class
# runs them against a collision mesh. crates/game-sim/src/collide.rs is the port and
# crates/game-sim/tests/collide.rs the proof; research/journal/2026-10-15-s4-s4-collision has the
# reconnaissance, including the classes and the call chain that reaches this.
mesh_sweep                  boot 0x0010f460 the entry the mesh classes call: stashes the vertex
#                                           descriptor in the global at 0x00468a78, shifts the
#                                           remaining arguments down and tail-calls the sweep below.
#                                           (bundle, child word, &{nodes, triangles}, descriptor,
#                                           record, 1) with the parent's live-probe mask in t1 — 0 at
#                                           the top call
mesh_sweep_level            boot 0x0010cfa0 one level of the descent, and the leaf test. Recursive:
#                                           bumps PTR 0x0041daa0 (the scratchpad cursor, 0x70000000)
#                                           by 0x40, copies the parent's sixteen live-probe words into
#                                           its own block (0x0041dab0 = all ones for the top level),
#                                           then either tests the node's box or the leaf triangle.
#                                           Node: whole bundle first (|centre - bundle centre| <= half
#                                           + radius per axis), then the first live probe that reaches
#                                           the box descends *both* children and the probes before it

#                                           the two edges, vec3_normalize, backface cull (normal.dir
#                                           must be < 0), t = normal.(v0 - origin)/normal.dir inside
#                                           0..length, then the containment test — flatten onto the two

#                                           and 256 levels, both because of where the mask lives

#                                           vertices by index, w = 1.0. Descriptor is {array, per-
#                                           vertex normals or 0, packed}; wide is three floats at
#                                           index*0xc, packed three shorts at index*6 scaled by
#                                           0x38000100 (a rounded 1/32767) and then by 32767.0
#                                           (0x004206d8) — in that order, which is not what the
#                                           decompilation prints
#
# In memory (not on the disc): a tree node is 0x24 bytes — key at +0, |half| at +4, child words at +8

# u16 vertex indices at +0. The collision record, as the sweep uses it: +0x20 nearest normal, +0x30

# +0x120 count, +0x12c/+0x130/+0x134 the origin/direction/length arrays, +0x140 centre, +0x160 radius.

# The rest of the subsystem, read but not ported here:

#                                           bundle's sphere, dispatches on the other object's class at

# V5 — the motions themselves: what a clip looks like. The port is crates/game-render/src/skin.rs and
# the proofs are crates/game-render/tests/skin.rs. How each one was found is in
# research/journal/2026-10-16-v5-v5-motion-clips.
#
# The chain: motion_blend_one (S6, above) walks the clip's two channel lists, samples each channel at
# phase * duration through its vtable (+0x10 rotation, +0x14 position), maps the channel's name index
# through the clip's own name->joint byte array (0xff = skip the channel), cross-fades the sample
# against the blend buffer the restart snapshotted, and writes the joint record at motion+0x234,
# stride 0x60: +0x40 the translation, +0x50 the quaternion, +0x34 the transform node they are pushed
# into. motion_blend_two does the same with both clips sampled at the same seconds.
# The rotation channel comes in two classes, one per key kind, picked by the clip's +0x2c when
# motion_channels_new allocates them. Both are 0x1c bytes with the same fields (+0 name index, +4 the
# on flag, +8 the key count, +0x14 the key array, +0x18 the cached pair) and the same vtable shape,
# whose +0x10 is the sampler and +0x20 the "reserve n keys". Kind 1 (twelve-byte keys) is the vtable at
# 0x0044dce0; kind 0 (eight-byte keys) is 0x0044dd10, and its sampler and decoder are the same code
# over bytes instead of shorts.
# Both rotation samplers have a path for a channel of fewer than three keys that weights the pair from
# the float *in front of* the key array — the allocator's own bytes. It is reachable: two rotation
# channels on the disc have two keys (Tracks\free10_ss.res :: tracks\free10_ss\anim\sh_windsock.mot).
# The port weights those from the first key instead, which is the same clip with a defined weight.
motion_rot_sample           boot 0x00136880 (seconds in f12, channel in a0, out in a1) a rotation
#                                           channel's quaternion: the cached-pair hint and its two
#                                           guesses, a forward then a backward walk, then
#                                           motion_quat_slerp_keys over the pair. Writes nothing when
#                                           the channel is off (+4) or empty. Held at the ends — and
#                                           before the first key it holds key *1*, not key 0, which
#                                           is the index its fallback uses
motion_rot_sample_narrow    boot 0x00136de0 (seconds in f12, channel in a0, out in a1) the same
#                                           sampler for the eight-byte key: the same hint, the same
#                                           two walks, the same held ends and the same key-1 fallback,
#                                           with a stride of 8 and motion_quat_slerp_keys_narrow
motion_pos_sample           boot 0x00137e70 (seconds in f12, channel in a0, out in a1) a position
#                                           channel's translation, w = 1. Past the last key it
#                                           extrapolates along the last interval rather than holding.
#                                           Its other path — channel off, or fewer than two keys —
#                                           writes the key's z into x and never writes z at all; no
#                                           clip on this disc has fewer than six keys in a channel
motion_pos_bracket          boot 0x001380b0 (seconds in f12, keys in a0, count in a1, out a/b/u) the
#                                           binary search the position sampler uses: -> false and the
#                                           last two keys when the time is at or past the last, and
#                                           with a time before the first key it brackets keys[-1]
motion_quat_decode          boot 0x00100a50 (key in a0, out in a1) one 8-byte rotation key as a
#                                           quaternion: axis * sin/32767 with the cosine's sign folded
#                                           in, w = |cos|, so w is never negative
motion_quat_decode_narrow   boot 0x001008e0 (key in a0, out in a1) the four-byte rotation: a u8 turn
#                                           index into motion_turn_table_narrow and three i8 axis
#                                           components, otherwise identical to motion_quat_decode
motion_quat_slerp_keys      boot 0x0013f000 (weight in f12, key a in a1, key b in a2, out in a0)
#                                           decodes both keys and hands them to motion_slerp with the
#                                           shortest-path flag set, which is the only caller that sets
#                                           it
motion_quat_slerp_keys_narrow boot 0x0013ef20 (weight in f12, key a in a1, key b in a2, out in a0) the
#                                           same for two four-byte keys
transform_set_rotation      boot 0x001b2130 (transform in a0, quaternion in a1, 0 in a2) writes the
#                                           quaternion as three rows at +0x40/+0x50/+0x60 — the
#                                           row-vector form, the transpose of the textbook one — then
#                                           marks the chain dirty. a2 non-zero loads the identity
#                                           instead
transform_dirty             boot 0x001b1930 (transform) the "this frame's matrix is stale" mark
#                                           transform_set_rotation ends in; hooked in the proofs
# 0x001b3060 (out, transform, p) -> p turned into the transform's frame without its origin; the
#   mirroring path's half of transform_unpoint. Named `orientation_transform_point` above — V5 found
#   it independently and called it `transform_rotate`, but S19 gave that name to 0x001b2ff0, a
#   different function, and its tests resolve it. Use the established name; nothing in V5 resolves
#   this one.
#
# The two tables the quaternion code reads. Both are built at start-up into memory nothing in the
# image's call graph writes, so the port rebuilds them from sin/cos/acos; a save state's copies agree
# to 1.8e-7 and 1.1e-5. Addresses, not functions.
motion_turn_table           boot 0x0045fa20 4096 entries of (f32 sin(n*pi/4096)/32767, f32
#                                           cos(n*pi/4096)), stride 8. The cosine's sign bit is the
#                                           one motion_quat_decode folds into the axis
motion_turn_table_narrow    boot 0x00467a20 256 entries of (f32 sin(n*pi/256)/127, f32 cos(n*pi/256)),
#                                           stride 8: the same table for the four-byte key, and it
#                                           sits immediately after the wide one (0x45fa20 + 0x8000)
motion_arc_table            boot 0x0046a688 a pointer to 30002 f32 of acos(i/14999.5 - 1) — 0x0062eaa0
#                                           in the save state. The last two live entries are
#                                           0.00048828125, not an arc cosine of anything, and the
#                                           slerp reads them for any dot product above 0.99997
motion_arc_scale            boot 0x0046a6a0 14999.5: the f32 a dot product's magnitude is scaled by,
#                                           and also the table's own middle
motion_sine_poly            boot 0x00426e10 the slerp's sine series: 1, -1/6, 1/120, -1/5040
motion_slerp_one            boot 0x0041f730 1.0: the dot product at or past which the slerp returns
#                                           its `from` untouched instead of dividing by sin 0

motion_clip_read            boot 0x00142750 (archive in a1, clip in a2) the `.mot` reader: the version

motion_channels_new         boot 0x00140c80 (clip, count) the rotation channel array: an array of

motion_rot_channel_new      boot 0x00135cd0 (chan) a rotation channel: +4 = 1 on, +8 = 0 keys,

motion_rot_channel_new_narrow boot 0x00135c00 (chan) the same for the eight-byte key kind, with the

motion_pos_channel_new      boot 0x00135900 (chan) a position channel: the same without the cache

# S20 — the animation caller: the clip table each rider state asks a clip out of, the one function in
# the game that starts a clip-to-clip transition, the pose snapshot a cross-fade fades from, and the
# fourth arm of the library dispatch. The port is the same crates/game-sim/src/motion.rs the S6 block
# above describes, the proofs are crates/game-sim/tests/motion.rs, and how each one was found is in
# research/journal/2026-10-16-s20-s20-animation-caller.
#
# Two corrections to the S6 block. motion_blend_three takes *four* clip handles, not three — three
# weights over two pairs: a/b mixed by f13, c/d mixed by the same f13, the two results mixed by f14.
# And +0x4c of the motion object is not "which transition sampler": it is the clip handle a running
# transition is coming out of, written by motion_play below. Its *nullness* picks the sampler, because
# a transition out of a real clip samples that clip at the fade clock (+0x88) while one out of nothing
# samples the pose snapshot instead -- both of them weighted by the same smooth step.
#
# The dispatch itself is at the tail of stunt_clocks: `./kit dis 0x259b00 0x259c00`. The mode lives in
# $17 and the whole function writes it exactly four times -- 0 in the prologue, 2 in the airborne arm,
# 1 in the two arms that end on the neutral pose -- so the rider reaches modes 0, 1 and 2 and nothing
# else. $21, $22 and $23, the arguments past the handles, are zeroed in the prologue and never written
# again, which is why Ghidra prints them as literal zeros. Mode 3 is not a case in either copy of the
# dispatch: a 3 falls out of the bottom and the frame makes no call at all.
vehicle_animation boot 0x002492b0 the vehicle's own animation step, which is the second copy of the
#                                same dispatch (`./kit dis 0x249b20 0x249c40`) and has a sixth arm at
#                                mode 5. It is the caller for the four-clip blend: it writes 4 into
#                                $17 at 0x002497b4 and 0x002498d4, two arms of a 60-entry jump table
#                                (0x00431990, indexed by its own animation state at +0x8f0) that each
#                                pick two pairs
#                                of clips out of its own tables at +0x960..+0x980 and hand them over
#                                with the within-pair mix in f13 and the between-pair mix in f14.
#                                Ghidra drops both of those blocks. Not ported: it is a different
#                                object's animation, and only the shape of the call it makes is here
motion_play boot 0x001464a0 (length in f12, motion in a0, clip handle in a1, keep the phase in a2)
#                          put a clip on. The only writer of +0x80 anywhere, so every clip-to-clip
#                          transition in the game starts here -- and nothing in the rider's animation
#                          section calls it. Its four callers are the wrapper below, the vehicle's
#                          animation step at 0x002496e4 (fade length from its own +0x690, the clip out
#                          of its table at +0x900, phase not kept, and mode 0 after), and two other
#                          actors at 0x0032b138 and 0x0032ea40. length 0 is a hard cut: +0x3c = 0,
#                          +0x48 = the clip, +0x80 = 0, +0x84 = 0. Otherwise the transition: +0x90 and
#                          +0x88 = the old clip time, +0x8c = that plus length, +0x94 = length,
#                          +0x4c = the old clip -- and if there was no old clip, or a transition was
#                          already running, +0x4c = 0 and anim_rewind takes the pose snapshot instead.
#                          Then +0x48 = the clip, +0x84 = 0, +0x80 = 1. With a2 set, the clip time is
#                          carried across as new.duration * (old time / old.duration): computed from
#                          the old clip *before* any of this and written over +0x84 after all of it

# no-hander it drives when the bike is not balancing, all four of them listed but not ported by S3.
# The port is crates/game-sim/src/move.rs (stand_upright, balance, roll_pitch, no_hander) and the
# proofs are in crates/game-sim/tests/move.rs; how each one was found is in
# research/journal/2026-10-16-s17-the-rider-controllers. The four addresses are in the S3 block above.
#
# All four are read through `./kit dis`, not the decompiler: every one of them builds its accumulator
# chain in an order Ghidra reorders, and one of them calls a function with seven register arguments,
# which Ghidra prints as a call with two.
#
# bike_stand_upright 0x002574e0 — the low-speed upright controller. Only with both wheels down, not
#   balancing, no throttle and |speed| < 10 (a literal, not a key). It takes the part of gravity that
#   runs along the ground — gravity less its component along the front wheel's contact normal — splits
#   that into the part along the chassis' forward axis flattened into the contact plane and the part
#   across it, and pushes back: minus the across part always, minus the along part as well while the
#   brake is held. The forward axis comes from orientation_axes against the chassis' own transform,
#   which may be null; the function does not check, and the null answer is (0,0,1,0). A flattened
#   forward of exactly zero length makes it give up and add nothing.
# bike_balance 0x002561f0 — balance on one wheel. Only with the front wheel in contact. Four
#   accumulators, all of them at +0xa4c..+0xa6f and all of them zeroed by the step whenever the bike
#   is not balancing (S3 read that clearing as the no-hander's; it is this one's):
#     +0xa4c balance_inertia      the rate the rider's input is let through, ramped by
#                                 BalanceInertiaRate between MinBalanceInertia and MaxBalanceInertia
#     +0xa60 balance_command      the command the stick and the noise make, clamped to +-1
#     +0xa64 balance_point        the lean the command integrates to, clamped to +-MaxBalancePoint
#     +0xa6c balance_noise_time   the noise's own clock
#   The roll angle it controls to comes from the front wheel's contact normal (front+0x130) brought
#   into the bike node's frame, flattened into the frame's xy plane, normalised, and read off the acos
#   table — the same lookup air.rs::AcosTable::at already is. The controller is a P term on that angle
#   less the roll rate (chassis+0x290's z) and less the disturbance the balance point commands, and
#   what it moves is the chassis' centre of gravity in x, clamped to +-RollControlMaxCG.
# bike_roll_pitch 0x00256470 — the roll and pitch the rider's lean feeds, on the ground only. Two
#   halves, each a PI controller on a pitch rate with the integral at +0x724:
#     the wheelie — rear wheel down, throttle on, speed over 5 (a literal), the *rear* brake off
#       (+0x654), no clutch, and the stick pulled back past 0.5. The command fades out with speed
#       through +0x720's 1/WheelieTopSpeed.
#     the stoppie — latched at +0x728 by the *front* brake (+0x650) and the stick pushed forward past
#       -1, and dropped
#       again below -0.1 of stick or under 7 of speed. It adds a yaw term as well:
#       1000 * (StoppieYawRateScale * lean - the rate about the rear contact normal).
#   The wheelie half measures the same rate against the same normal and multiplies the result by a
#   literal zero, so that whole dot product is dead.
# bike_no_hander 0x00255d20 — rolls the bike node about its own forward axis so the rider can let go.
#   The angle it rolls towards is the ground's roll angle under whichever wheels are properly down
#   (a ray hit, or a swept contact whose normal is more than 0.17 up), faded out with speed, with the
#   rider's lean commanding a roll up to MaxRollCommand — widened by DonutRollAngleScale while the
#   donut is on — and RollGain * dt of first-order lag on the way. It ends in transform_set_axes.
transform_set_axes boot 0x001b1e20 (node, relative_to, forward, up, sync_a in t0, sync_b in t1,
#                                  sync_c in t2) -> builds the node's world matrix from two axes by
#                                  Gram-Schmidt: row0 (+0x40) = forward x up, row1 (+0x90) = up,
#                                  row2 (+0xa0) = forward, row3 the translation it keeps. The pair
#                                  orientation_axes reads back out, which is how a2 is known to be the
#                                  forward (z) axis and a3 the up (y) axis. Ghidra prints the
#                                  orthonormalising callee (0x0013e330) as a two-argument call; it
#                                  takes five, in a2, a3, t0, t1 and t2, passed straight through
# The two brake words the two halves read are not copies of one another: the bike's setup at
# 0x002535a0 hands the front wheel a pointer to bike+0x650 as its +0x30 and the rear wheel one to
# bike+0x654, beside the engine's +0x658/+0x65c (the rate-limited throttle and clutch), and each wheel
# reads its own word as a brake — 0x0025c4c8 in wheel_surface_drag turns it into a torque against the
# spin, 0x0025cb8c in wheel_tire_forces gates the locked-wheel path on it being nonzero. So the
# wheelie's veto is the driven wheel's brake and the stoppie's gate is the front's. Who writes the two
# words (one lever into two rate limiters, or two levers) was not chased down; the port keeps them as
# two inputs, Step::front_brake and Step::rear_brake.
# rotate_about_axis 0x001344e0 (the S7 block has it: angle in f12, unit axis, v, out) is the
# no-hander's last arithmetic — the ground normal turned about the node's own forward axis by minus
# the angle. Ported and proved by S7 as camera::rotate.
# The .phy keys the four controllers read, on top of S3's table. The loader is bike_phy_load
# 0x002539e0; a default in brackets is the one the loader passes when the key is absent.
#   DonutRollAngleScale       +0x540  [1.0]  (loaded at 0x00255380, far down the same function)
#   MaxRollCommand            +0x6d8  * 0.01745329 (degrees)
#   MaxRollSpeed              +0x6e0  * 1.46666
#   RollGain                  +0x6e8
#   MinStandUprightSpeed      +0x6ec  [10.0] * 1.46666
#   MaxStandUprightSpeed      +0x6f0  [30.0] * 1.46666
#   RollControlGain           +0x704
#   RollControlRateGain       +0x708
#   RollControlMaxCG          +0x70c
#   MaxRollRateDisturbance    +0x710
#   MaxPitchCommand           +0x714  * 0.01745329
#   PitchGain                 +0x718
#   PitchRateGain             +0x71c
#   WheelieTopSpeed           +0x720  stored as 1.0 / (key * 1.46666)
#   MaxStoppiePitchCommand    +0x730  * 0.01745329
#   StoppiePitchGain          +0x734
#   StoppieYawRateScale       +0x738
#   StoppieTopSpeed           +0x73c  * 1.46666
#   BalanceInertiaRate        +0xa50
#   MinBalanceInertia         +0xa54
#   MaxBalanceInertia         +0xa58
#   InputInertia              +0xa5c
#   BalanceNoiseAmplitude     +0xa68
#   BalanceNoiseTimeScale     +0xa70
#   MaxBalancePoint           +0xa74
#   StoppieBrake              +0x72c  the loader writes it and the pitch controller never reads it:
#                                 the stoppie latch at 0x002566a0 compares
#                                 the front brake (+0x650) against a zero built with `mtc1 $zero`,
#                                 and nothing in 0x00256470..0x00256940 touches +0x72c. pad_to_gesture
#                                 is what reads it. So it is a loader key and an input key, not one
#                                 of the ground step's twenty-five (S21)
