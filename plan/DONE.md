### Phase 4 — the arithmetic, before any ported math
- [x] **F1** The EE FPU in `crates/ps2-float`: add, sub, mul, div, sqrt with the PS2's rules — round toward zero, no denormals (flushed), no NaN or infinity (clamped to the largest magnitude), and the smaller addend masked to the exponent difference minus one guard bit. Port physics before this and you will not know which of the two is wrong → crates/ps2-float/src/fpu.rs | t: crates/ps2-float/tests/fpu.rs | j: f1-ee-fpu
- [x] **R5** (after R1) The RNG: find it (look for a 32-bit multiply by a constant and a stored seed, cross-referenced from everywhere), port it, and prove it with the oracle over 10k calls from a dumped seed. A wrong RNG makes every later proof noisy, and it is a 20-line function → crates/game-sim/src/rng.rs · research/oracle.txt | t: crates/game-sim/tests/rng.rs | j: r5-rng
- [x] **F2** `madd.s`/`msub.s` and the accumulator: the product is truncated before the add, so a multiply-add is *not* a multiply then an add. Most of a PS2 game's vector math goes through these, so a wrong one shows up as a tiny drift that takes days to find → crates/ps2-float/src/fpu.rs | t: crates/ps2-float/tests/fpu.rs | j: f1-ee-fpu
- [x] **F4** (after O1) The game's own transcendentals: whatever `sinf`, `cosf`, `atan2f`, `sqrtf` and `powf` the disc links. They are rarely the standard library's, and a port that calls the host's `sin` will differ in the last bits of every angle. Port the disc's implementations and check them against the oracle over the full input range → crates/ps2-float/src/libm.rs (new) · research/oracle.txt | t: crates/ps2-float/tests/libm.rs | j: f4-libm
- [x] **F5** (after F3) The matrix and quaternion helpers the game uses for bones and cameras, built on F1–F3 with the same op order as the original (the order changes the last bits) → crates/game-sim/src/math.rs | t: crates/game-sim/tests/math.rs | j: f5-matrix
