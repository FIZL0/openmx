# S236 — a sim tick that fits a 90 Hz frame on the Steam Deck (user 2026-10-31)

The user felt regular lag spikes riding on the Steam Deck (OLED, 90 Hz, vsync Fifo, openMX 0.9.4).

## What the Deck showed

`--timings`, Supercross01[Quadzilla] freeride, 577 props, 23 traffic cars, 50 birds, one bike:

- per second: ~85 fps average, but **~30 frames a second over 16.7 ms**, worst 28.4 ms
- of 777 slow frames, **757 have `sim` as the biggest stage** (16-24 ms), the rest `present`
- the tick is 29.97 Hz (`pace::TICK`), so at 90 fps a tick lands on every third frame and that frame
  carries the whole tick: one tick ≈ 17-24 ms on the Deck's Zen 2, against an 11.1 ms frame

`perf record` of the ride (15 s, self time; the release binary is stripped, symbolised with
target/steamrt/release/openmx):

| share | what |
|---|---|
| ~33 % | libc: malloc/free internals and memcpy/memset |
| ~26 % | `ps2_float::vu::{add,mul}`, `ps2_float::fpu::{add,mul}` |
| ~10 % | `broad_build::insert`/`key`/`mesh_box`, `flight_search::{wooded_of, tree_box, Filing::file, world_unfiled}`, `Vec<Collidable>` drop, `Vec<broad_phase::Node>` clone |

## Why

`flight_search.rs`'s own comment (P205): "the ride builds its worlds afresh for every search, three or
more a tick". Each search runs `world_unfiled` (a `Collidable` and a `Placement` per prop — 577 here),
builds a `Filing` stamp of 9 words per item, compares it with up to `FILED_KEPT` = 8 stamps, and on a hit
still clones the whole quadtree; then everything is dropped. That is the allocation and copying.

## The fix

Keep the built world (Broad + collidables + placements) between searches and between ticks while its
inputs are the same (the prop set, the field, `toys`), and only move the probe objects (RAY/SWEEP) and
the moving toys for each search. The physics must not change: same contacts, same order, bit for bit.

## Proof

- game-sim test: a run of searches against a kept world and against a fresh world per search give
  identical results, bit for bit (including toys moving between ticks)
- `same_ride` / the existing ride tests unchanged
- a counter or bench that a steady ride does no per-search world build
- journal the Deck numbers before/after (`--timings` worst ms and frames over 16.7 per second)

If the tick is still over ~11 ms after this, the next lever is `ps2_float` (26 %): look for hot loops
doing scalar emulated maths that could stay in one representation; that is a separate task.
